# OmniTrig

统一录制、注册与管理键盘和鼠标组合的 Rust 触发引擎。

目标是让用户录下一个操作，就能将其注册为触发器，例如 `CapsLock + W`、`鼠标侧键 + 滚轮上滚`。触发器的绑定、分配与动作协调通过 API 交给代码或 Agent，减少重复的人类配置。

## 当前状态

项目处于设计与初始化阶段。当前尚未实现输入引擎、系统 Hook、录制器或图形界面；下文描述后续开发方向。

首个平台为 Windows，核心使用 Rust；管理和录制界面优先评估 GPUI。项目独立开发，核心不依赖其他产品代码。

## 核心设计

- **统一描述**：录制器生成 `TriggerSpec`，注册、冲突检查与运行时匹配共享这一份语义。
- **确定性状态机**：核心按 `InputEvent → Engine::process → Decision` 工作，输入标准化事件，输出透传、消费、触发通知及必要的补发计划。核心不依赖 UI 或 Windows API。
- **平台适配**：Windows 适配层负责采集输入、执行消费决策和补发；系统 Hook 的同步路径只做有界匹配，不执行动作、网络请求或 Agent 推理。
- **程序化协调**：通过 API 管理触发器与动作标识，动作执行与自动分配由调用方协调。冲突应返回结构化诊断，避免静默改变录制结果。
- **轻量界面**：GPUI 作为候选界面，负责录制、展示、编辑与必要确认，与核心引擎解耦。

## 输入语义边界

“任意组合”是模型的扩展目标，实际能力受系统与硬件提供的事件约束。

普通按键作为前缀时，须明确透传或延迟消费策略。例如 `CapsLock + W` 中，若要避免 CapsLock 提前生效，可暂存其按下事件，组合命中后消费整次按压，单独使用时再处理回退。延迟与补发会改变时序，不能承诺完全无损；按下、释放以及取消后的状态必须成对收尾。

首版需明确键盘自动重复、滚轮轴与高精度增量、自身注入事件、作用域切换和暂停后的恢复语义。设备区分按平台能力提供，不假定不同输入接口天然可以无歧义关联。

## 首版开发顺序

1. 纯 Rust 事件模型、`TriggerSpec`、匹配状态机与定向测试。
2. Windows 输入适配和最小宿主，验证真实输入的采集、消费与回退。
3. 录制与注册共用模型，提供增删改查及冲突诊断 API。
4. 评估并接入 GPUI 录制和管理界面。

首版验收重点：CapsLock 单击和组合、侧键单击和滚轮、未命中回退、重复按下与释放顺序、滚轮方向和增量、补发防递归、作用域切换时取消，以及重复注册和前缀冲突。
