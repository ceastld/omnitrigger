# 配置档与数据目录设计

状态：部分实现。

安装后的开始菜单提供“OmniTrigger”和“OmniTrigger 测试”。后者与开发入口 `start.ps1` 共用 `--test-workspace`，首次自动创建 `testing` 测试配置档，之后沿用。日常数据与测试数据均属于当前 Windows 用户，独立于安装目录，卸载和重装后保留。

- 已实现：数据根解析（`--data-root`、`OMNITRIGGER_HOME`、默认目录）、打包重定向检测与脱离重启、持久测试配置档（`--profile`、`--profile-create`、`--profile-reset`、`--profile-list`，种子 `empty`、`fixture:`、`copy:`）、测试配置档默认不安装 Hook 与 `--listen`、窗口标题和侧栏的测试数据标识、启动时发现更新的外部副本并询问导入。
- 首阶段的默认配置档就是数据根本身，文件仍在 `%LOCALAPPDATA%\OmniTrigger` 原位，尚未迁移进 `profiles\<ID>\`；`examples` 种子、单实例、运行中切换、自动备份、设置页管理界面和账号关联尚未实现。
- `--config` 保持原有行为（照常安装 Hook），不能与配置档参数同用。

本页解决四个问题：

- **数据分裂**：从打包应用（例如桌面 Agent 客户端）的终端启动时，Windows 把 `%LOCALAPPDATA%` 的写入重定向到该应用的私有目录。从不同客户端启动，就各自读写一份数据，用户看到“刚才的数据不见了”，实际是读到了另一份副本。
- **测试数据没有家**：开发和自动化测试每次用 `--config` 指向临时文件，测试数据要么随手丢弃，要么散落各处，下次启动又是一份新数据，无法积累可复用的测试场景。
- **测试改到真实数据**：测试实例与日常实例使用同一目录时，截图、录制和保存会改动用户自己的绑定。
- **多实例重复触发**：程序没有单实例保护，多个实例同时安装 Hook，同一组合触发两次，还可能互相覆盖配置。

账号、云同步和存储引擎的设计见[账号工作区与同步设计](ACCOUNT_WORKSPACE.md)，本页定义它们在本机依赖的配置档层。

## 概念

| 概念 | 含义 |
| --- | --- |
| 数据根 | 本机唯一的 OmniTrigger 数据目录，所有配置档和本机数据都在其下。任何启动方式都必须解析到同一个数据根。 |
| 配置档 | 一份完整、相互隔离的用户数据：动作、绑定、轮盘、动作包、外观和浏览器连接设置。一个实例同一时刻只使用一个配置档。 |
| 配置档类型 | 本地、账号、测试三种，见下表。 |
| 本机数据 | 与配置档无关、只属于这台机器的数据：插件运行时、程序路径映射、设备映射、窗口位置。 |
| 运行期数据 | 命中次数、触发记录、诊断统计。只在本次运行的内存中，不属于任何配置档，切换或重启后清零。 |

| 类型 | 用途 | 同步 | Hook | 外观标识 |
| --- | --- | --- | --- | --- |
| 本地 | 默认类型，即“离线账号”。未登录也能完整使用，之后可以关联账号。 | 不同步 | 安装 | 无 |
| 账号 | 已关联 OmniTrigger 账号，离线照常使用，联网后后台同步。 | 同步 | 安装 | 显示账号名 |
| 测试 | 演示、截图、开发与自动化验证；数据持久保留，可反复使用，也可一键重置。 | 永不同步 | 默认不安装 | 醒目的“测试数据”色块 |

离线账号不单独建模：本地配置档就是离线账号，关联账号后转为账号配置档，ID 和数据不变。

## 数据根解析

数据根按以下顺序确定，第一个命中的生效，结果在启动日志和“设置 → 配置档”中显示：

1. 命令行 `--data-root <目录>`，仅用于开发和隔离测试整套数据根。
2. 环境变量 `OMNITRIGGER_HOME`。
3. 默认值：当前用户真实的 `%LOCALAPPDATA%\OmniTrigger`。

“真实”的含义由重定向检测保证：

- 启动时在数据根中创建或打开一个探针文件，用 `GetFinalPathNameByHandle` 取得文件的最终路径。若最终路径落在 `%LOCALAPPDATA%\Packages\<包名>\LocalCache\` 之下，说明当前进程运行在打包应用的重定向上下文中。
- 检测到重定向时不加载任何配置档：在 `%TEMP%\OmniTrigger` 写一个指向程序真实路径的快捷方式，交给 `explorer.exe` 打开，新进程由系统外壳创建，不继承打包上下文；原配置档参数原样转交，当前进程退出。在创建子进程时请求脱离桌面应用策略的做法经实测无效，未采用。
- 只有直接启动界面（可带 `--profile`）和配置档命令会探测与重启。配置档命令重启后把结果写入临时文件，由原进程读取并照常输出到命令行。其他命令行入口不探测，行为与以前相同。
- 重启后仍处在重定向中时显示阻断提示：说明当前读写的目录、真实数据根的位置，以及可用 `--data-root` 显式指定；不静默使用重定向目录。
- 探针是关闭即删除的临时文件，只判断路径，不读取或修改用户数据。

## 目录结构

```text
<数据根>\
  profiles.json                  配置档目录：列表、默认配置档 ID、类型、显示名、创建来源
  profiles\<配置档 ID>\
    bindings.json                用户数据；文件名沿用现状，迁移到 SQLite 后改为 workspace\
    wheels.json
    appearance.json
    browser-connector.json
    plugins.json
    actions\                     托管动作包
    backups\                     该配置档的自动备份
    sync\                        同步元数据（仅账号类型）
    profile.json                 配置档自述：ID、类型、显示名、来源、种子版本
  device\                        本机数据：程序路径映射、设备映射、窗口状态
  plugins\                       插件运行时缓存，各配置档共享
  imports\                       发现的外部副本导入前的只读快照
```

- 现有代码的所有数据文件都由 `bindings.json` 所在目录推导，因此“一个配置档 = 一个目录”可以直接映射：选中配置档等价于把该目录作为配置路径。首阶段不改文件格式。
- 配置档 ID 是创建时生成的随机稳定 ID，不使用显示名、账号邮箱或测试场景名作目录名；改名不移动目录。测试配置档另有便于命令行引用的**别名**，见下文。
- 链接目录动作包的路径属于本机数据，存于 `device\`，不进入配置档。

## 测试配置档

测试配置档是持久的：同一个别名每次启动都读写同一份数据，测试中做的修改、录制的绑定和轮盘都保留到下次，直到显式重置。

### 创建与引用

| 命令 | 作用 |
| --- | --- |
| `--profile <别名或 ID>` | 使用指定配置档启动。别名不存在时报错退出，不隐式创建。 |
| `--profile-create <别名> [--type test] [--seed <来源>] [--name <显示名>]` | 创建测试配置档后退出。来源为 `empty`（默认，即程序默认数据）、`fixture:<目录>`，或 `copy:<别名或 ID>`，`copy:default` 复制日常数据。合并仓库示例的 `examples` 来源尚未实现。 |
| `--profile-reset <别名>` | 用创建时记录的来源重新生成数据；原目录整体移入 `backups\profile-reset\`。仅测试类型可用。 |
| `--profile-list` | 以 JSON 输出所有配置档的 ID、别名、类型、目录与默认标记。 |

- 别名限定为小写字母、数字和 `-`，在数据根内唯一。界面同样可以创建测试配置档，命令行与界面写同一份 `profiles.json`。
- 种子与复制只取顶层数据文件和托管动作包 `actions\`，跳过锁文件、`.bak` 旧备份、插件运行时与 `device\`；“来自 X 的副本”的界面标记尚未实现。
- 测试夹具放在仓库内（例如 `tests\fixtures\profiles\<场景>\`），作为版本控制下的种子；配置档本身在数据根中，不进入仓库。

### 测试实例的运行约束

- 测试配置档默认**不安装 Hook**，只打开界面，避免与日常实例重复触发；需要验证真实输入时显式加 `--listen`，此时与日常实例的冲突规则见下节。
- 窗口标题带配置档显示名，例如 `OmniTrigger — 测试：浏览视图`，便于自动化按标题定位窗口和截图，不会误操作日常实例。
- 测试实例不修改 `profiles.json` 中的默认配置档，不影响下次正常启动。

### 自动化与 Agent 的推荐流程

1. 首次：`--profile-create ui-browse --seed fixture:tests\fixtures\profiles\ui-browse --name 浏览视图` 建立一个覆盖键盘、鼠标、滚轮和应用范围的测试配置档。
2. 每次验证：`--profile ui-browse` 启动，检查后退出；数据保留，下次继续使用。
3. 场景被测试改乱时：`--profile-reset ui-browse`。
4. 需要真实输入：`--profile ui-browse --listen`，验证完立即退出。

## 单实例与切换

单实例按“是否安装 Hook”划分：

- 安装 Hook 的实例在每个 Windows 用户会话内只允许一个，以会话内命名互斥量保证。后启动的实例把命令行参数（打开窗口、`--profile`、`--panel` 等）转交给已运行的实例后退出；要求的配置档与当前不同时，由已运行实例在界面中询问是否切换，不静默切换。
- 不安装 Hook 的测试实例可以与日常实例并行，每个配置档至多一个实例，以配置档 ID 命名的互斥量保证，避免两个实例同时写同一目录。
- 测试实例加 `--listen` 而日常实例已在监听时，拒绝启动监听并说明原因；不抢占日常实例的 Hook。

切换配置档在运行中的实例内完成，不需要重启：

1. 取消正在进行的前缀暂存、长按、面板和轮盘；已消费的按下补齐释放，与暂停监听的收尾规则相同。
2. 停止旧配置档的同步任务，撤下触发快照。正在执行的动作继续完成，回执带配置档代次，不写入新配置档。
3. 加载新配置档，通过冲突检查后整体替换触发快照；失败时保留旧快照并显示结构化错误。
4. 记录新的默认配置档，下次启动沿用。

输入核心只接收新的快照，不感知配置档。

## 外部副本的发现与导入

当前实现：以默认数据根直接启动界面时，扫描 `%LOCALAPPDATA%\Packages\*\LocalCache\Local\OmniTrigger\`，取比当前数据更新、且未被忽略的最新一份，用对话框询问：导入（当前数据先复制到 `backups\before-import-<时间>\`，再复制副本的顶层数据文件与 `actions\`；不复制插件运行时）、忽略（记入 `device\external-copies.json`，有新修改时再提示）或本次不处理。以下是完整设计：

- 每份副本列出来源包名、最后修改时间、绑定与轮盘条数，以及与当前数据的差异摘要。
- 用户逐份选择：导入为新配置档、替换当前配置档的数据（先备份），或忽略。不自动合并，不删除原副本。
- 导入前把副本复制到 `imports\` 作只读快照，导入失败不影响原副本和当前数据。
- 已忽略的副本记录其最后修改时间，之后有新的修改时再提示一次。

旧版 `--config <路径>` 保留为开发入口，表示临时配置档：直接读写该文件所在目录，不进入 `profiles.json`，不同步，界面显示“临时数据”标记，默认不安装 Hook。

## 备份与恢复

- 每次保存前，把将被覆盖的文件放入该配置档的 `backups\`。保留最近 20 次，另外每天保留一份，最多 30 天。
- 迁移、导入、重置、同步合并和切换前的冲突处理，额外创建一份带原因标记的快照。
- 设置中可按时间查看备份、恢复为当前数据，或另存为新配置档。恢复本身也先备份当前数据。

## 迁移

首次升级到配置档版本时：

1. 解析真实数据根；处于重定向上下文时先按上文脱离。
2. 把根目录下现有的 `bindings.json`、`wheels.json`、`appearance.json`、`browser-connector.json`、`plugins.json` 和 `actions\` 复制进一个名为“我的配置”的本地配置档，设为默认；原文件保留在原位置，并写入迁移标记，迁移可重复执行且不重复导入。
3. 扫描并提示外部副本，处理方式见上节。

## 与账号的关系

| 操作 | 行为 |
| --- | --- |
| 本地配置档关联账号 | 云端为空时上传；云端已有数据时由用户选择：使用云端、上传本地或另存为新配置档。不自动合并、不覆盖。 |
| 新设备登录 | 新建账号配置档并下载数据；本机已有的本地配置档保持不变。 |
| 退出登录 | 停止同步、清除会话凭据，配置档转为本地类型继续可用，并标记“已退出，未同步”。 |
| 删除 | 删除本机配置档、删除云端数据和退出登录是三个独立操作，均需确认。 |

- 每个配置档最多关联一个账号；同一账号在本机只对应一个配置档。
- 测试配置档不能关联账号；需要同步时先复制为本地配置档。
- 本机数据（`device\`、`plugins\`）与运行期数据不随配置档或账号同步。

## 界面

- 侧栏监听状态卡下方显示当前配置档名称；测试和临时配置档使用醒目色块，一眼可见当前不是自己的数据。
- 点击配置档名称弹出切换列表：选中即切换，列表底部是“管理配置档”。
- “设置 → 配置档”是管理入口：新建（空白 / 从示例 / 复制当前）、改名、重置测试数据、导入外部副本、导入导出、备份恢复和关联账号；同时显示数据根位置及其解析来源。

## 实现顺序

1. 数据根解析与重定向检测：探针、脱离打包上下文重启、无法脱离时阻断提示，`--data-root` 与 `OMNITRIGGER_HOME`。
2. 配置档目录与 `profiles.json`，旧数据迁移为“我的配置”；`--profile`、`--profile-list`，窗口标题显示配置档。
3. 测试配置档：`--profile-create`、`--profile-reset`、`examples` 与夹具种子，默认不安装 Hook，`--listen`。
4. 单实例：监听实例互斥与参数转交，测试实例按配置档互斥。
5. 外部副本发现与导入，保存前自动备份与恢复。
6. 运行中切换配置档，侧栏标识与设置页管理界面。
7. 账号关联与同步，按[账号工作区与同步设计](ACCOUNT_WORKSPACE.md)的实现顺序推进。

每一步都以独立数据根运行集成测试：同一测试别名两次启动读到相同数据、重置后恢复种子、重定向探针在模拟路径下判定正确、两个监听实例只有一个安装 Hook。
