# 配置档与数据目录设计

状态：部分实现。

安装后的开始菜单提供“OmniTrigger”和“OmniTrigger 测试”。测试入口与开发入口 `start.ps1` 共用 `--test-workspace`，首次自动创建 `testing` 测试配置档，之后沿用。日常数据与测试数据均属于当前 Windows 用户，独立于安装目录，卸载和重装后保留。同一 Windows 会话再次打开同一入口会唤回原窗口，日常和测试窗口可同时使用。

在测试档使用从日常档复制的 N10 剪贴板切换热键或轮盘槽位，会打开本档的文本历史。要测试独立的 EaClip 数据库，可以在测试绑定中显式选择 `script-test` 并填写测试库路径。两种方式同样适用于已有测试档和 `--listen` 模式。[剪贴板动作配置](../examples/actions/n10-rust/README.md)

如果日常热键直接运行 EaClip 的 `search-toggle`，并用 `--host` 指向同目录的 `cliphost-gpui.exe`，在测试档触发它会聚焦本档主窗口的文本历史筛选框。再次触发会保留搜索词。测试档可筛选摘要或查找正文，日常档继续使用 EaClip 聚合搜索。此处理适用于使用绝对路径的 `eaclip-cli.exe` 和宿主，允许附带 `--json`。显式指定数据目录或其他选项的命令仍按保存的参数执行。

要用自己的热键和轮盘做测试，在日常窗口选择“设置 → 打开测试副本”。首次使用会复制日常档已保存的配置和动作包，打开名为“日常配置副本”的测试窗口，默认关闭全局监听。再次点击会沿用该副本及其修改。开始菜单的“OmniTrigger 测试”继续打开原来的 `testing` 配置档。

要继续使用已有测试档，在日常窗口选择“设置 → 查看已有测试档”。列表只读取当前数据根的登记，按名称和别名排列。名称相同的档案可通过名称下方的别名区分。点击对应行的“打开”，会按其原 ID 打开独立的测试窗口，默认关闭全局监听。保留数据目录重装后仍可使用这个入口。

即使你用命令行创建了同名、同种子的测试档，设置也会单独保留自己的副本。旧版没有记录创建来源，首次打开时会按显示名“日常配置副本”、种子 `copy:default` 和旧版别名识别。有多个完全匹配的旧档时，采用编号最小的一个。编号中间有空位时也能找到原副本，选定后按配置档 ID 记录来源。

如果上次重置在替换目录时中断，“打开测试副本”会先从该次重置的备份恢复原副本。副本目录缺失且没有对应的重置现场时，设置页会显示缺失的目录，保留已有备份和登记。

创建或重置副本时，程序会一起读取来源档的热键和轮盘。如果另一窗口正在保存其中一项，本次操作会提示稍后重试。重置遇到这种情况时，已有测试档中的修改会保留。

用 `copy:<别名>` 或备份种子从测试档创建副本时，程序会记住来源的配置档 ID。恢复备份后即使来源改了别名，重置仍使用原档。原档缺失时会指出要找回的 ID，保留副本里的修改。旧版仅记有普通别名的副本沿用当前登记，首次成功重置后把所用来源保存在副本的 `backups/seed-source.json`。手工备份时请一并保留这个文件。如果旧别名恰好长得像配置档 ID，且只能找到匹配的别名，可以从确认过的来源新建副本。

Windows 短暂占用测试档目录时，创建、重置和中断恢复会在同一次操作中重试改名。目录持续被占用时，程序会报告失败；关闭占用后可用原命令重试。正在使用测试档的窗口仍须先关闭才能重置。

如果导入外部配置时程序中断，复制日常档或从日常档的编辑备份创建、重置测试副本时，程序会先恢复日常档，再读取选定版本的热键、轮盘和配套动作包。恢复遇到文件占用或后续编辑时，程序会报告原因并保留现有测试档。把其他目录当作夹具或外部副本读取时，若该来源有未恢复的导入，可以先恢复来源，也可以显式选择其 `backups/before-import-*` 中对应的完整备份。

新建测试档时，程序先把热键、轮盘、扩展和身份文件完整写入 `.creating` 目录，再登记配置档并将副本移到正式目录。复制中途退出时，未登记的暂存目录不会列入配置档。如果登记成功后退出，用相同参数重试创建、打开该档或从它复制，都会继续使用已准备好的副本，即使种子数据已经改变。只读查询保留现场。

旧版留下的完整测试档目录若未列入登记，可用 `--profile-create <新别名> --seed fixture:<旧目录>` 将其复制为新档。如果已有配置档提示缺少 `profile.json`，可从备份恢复该身份文件。若提示指向未完成的新副本，可将该目录完整移到 `profiles` 之外，再用原入口重试。

- 已实现：数据根解析（`--data-root`、`OMNITRIGGER_HOME`、默认目录）、打包重定向检测与脱离重启、持久测试配置档（`--profile`、`--profile-create`、`--profile-reset`、`--profile-list`，种子 `empty`、`fixture:`、`copy:`、`backup:`）、测试配置档默认不安装 Hook 与 `--listen`、窗口标题和侧栏的测试数据标识、启动时发现更新的外部副本并询问导入。
- 默认配置档就是数据根本身，文件仍在 `%LOCALAPPDATA%\OmniTrigger` 原位。热键和轮盘编辑器已支持保存前备份，日常设置可以列出并打开已登记的测试档。`examples` 种子、运行中切换和账号关联尚未实现。
- `--config` 保持原有行为（照常安装 Hook），不能与配置档参数同用。
- 直接用 `--config`、`--data-root` 或 `OMNITRIGGER_HOME` 打开已登记的测试档时，任务栏和 Alt+Tab 中的窗口标题会显示“OmniTrigger — 测试：配置档名称”，侧栏也会显示该名称。关闭测试窗口会退出该实例。应用更新和更新后的启动确认由日常窗口处理。

如果用一个测试档作为数据根再创建子档，子档窗口和正在执行的动作会同时占用子档和外层测试档。重置任一档时会提示该档正在使用。关闭窗口或等待动作结束后即可重置，原有的历史、热键和轮盘会进入对应档的重置备份。

在测试档下面的子目录单独打开配置时，窗口显示最近一层已登记测试档的名称。热键、轮盘和文本历史仍从所选子目录读取，从日常档复制来的剪贴板切换动作也使用该子目录的文本历史。

`--tray` 只启动日常工作区。传入已登记的测试档或其中的子目录时，程序会在创建窗口锁和恢复重置备份之前退出。需要恢复该测试档时，从测试入口打开即可。

本页解决四个问题：

- **数据分裂**：从打包应用（例如桌面 Agent 客户端）的终端启动时，Windows 把 `%LOCALAPPDATA%` 的写入重定向到该应用的私有目录。从不同客户端启动，就各自读写一份数据，用户看到“刚才的数据不见了”，实际是读到了另一份副本。
- **测试数据没有家**：开发和自动化测试每次用 `--config` 指向临时文件，测试数据要么随手丢弃，要么散落各处，下次启动又是一份新数据，无法积累可复用的测试场景。
- **测试改到真实数据**：测试实例与日常实例使用同一目录时，截图、录制和保存会改动用户自己的绑定。
- **多实例重复触发**：普通主窗口按配置目录和监听模式复用。显式在不同配置档开启监听仍可能重复触发。

账号、云同步和存储引擎的设计见[账号工作区与同步设计](ACCOUNT_WORKSPACE.md)，本页定义它们在本机依赖的配置档层。

## 概念

| 概念 | 含义 |
| --- | --- |
| 数据根 | 本机唯一的 OmniTrigger 数据目录，所有配置档和本机数据都在其下。任何启动方式都必须解析到同一个数据根。 |
| 配置档 | 一份完整、相互隔离的用户数据：动作、绑定、轮盘、动作包、外观和浏览器连接设置。一个实例同一时刻只使用一个配置档。 |
| 配置档类型 | 本地、账号、测试三种，见下表。 |
| 本机数据 | 与配置档无关、只属于这台机器的数据：插件运行时、程序路径映射、设备映射、窗口位置。 |
| 运行期数据 | 命中次数、触发记录、诊断统计。只在本次运行的内存中，不属于任何配置档，切换或重启后清零。 |

| 类型 | 用途 | 同步 | Hook | 外观标识 |
| --- | --- | --- | --- | --- |
| 本地 | 默认类型，即“离线账号”。未登录也能完整使用，之后可以关联账号。 | 不同步 | 安装 | 无 |
| 账号 | 已关联 OmniTrigger 账号，离线照常使用，联网后后台同步。 | 同步 | 安装 | 显示账号名 |
| 测试 | 演示、截图、开发与自动化验证；数据持久保留，可反复使用，也可一键重置。 | 永不同步 | 默认不安装 | 醒目的“测试数据”色块 |

离线账号不单独建模：本地配置档就是离线账号，关联账号后转为账号配置档，ID 和数据不变。

## 数据根解析

数据根按以下顺序确定，第一个命中的生效，结果在启动日志和“设置 → 配置档”中显示：

1. 命令行 `--data-root <目录>`，仅用于开发和隔离测试整套数据根。
2. 环境变量 `OMNITRIGGER_HOME`。
3. 默认值：当前用户真实的 `%LOCALAPPDATA%\OmniTrigger`。

“真实”的含义由重定向检测保证：

- 启动时在数据根中创建或打开一个探针文件，用 `GetFinalPathNameByHandle` 取得文件的最终路径。若最终路径落在 `%LOCALAPPDATA%\Packages\<包名>\LocalCache\` 之下，说明当前进程运行在打包应用的重定向上下文中。
- 检测到重定向时不加载任何配置档：在 `%TEMP%\OmniTrigger` 写一个指向程序真实路径的快捷方式，交给 `explorer.exe` 打开，新进程由系统外壳创建，不继承打包上下文；原配置档参数原样转交，当前进程退出。在创建子进程时请求脱离桌面应用策略的做法经实测无效，未采用。
- 直接启动界面（可带 `--profile`）和配置档命令使用写入探针。单独运行 `--check-config` 会检查现有热键和轮盘文件的最终路径，检查测试档时还会检查登记文件。即使 Windows 只重定向了其中一个文件，也会经系统外壳检查同一数据根，并向终端返回检查结果和退出码。`--config` 仍直接检查指定文件。配置检查和动作命令均支持 `OMNITRIGGER_HOME` 与 `--data-root`。
- 重启后仍处在重定向中时显示阻断提示：说明当前读写的目录、真实数据根的位置，以及可用 `--data-root` 显式指定；不静默使用重定向目录。
- 探针是关闭即删除的临时文件，只判断路径，不读取或修改用户数据。

## 目录结构

```text
<数据根>\
  profiles.json                  配置档目录：列表、默认配置档 ID、类型、显示名、创建来源
  profiles\<配置档 ID>\
    bindings.json                用户数据；文件名沿用现状，迁移到 SQLite 后改为 workspace\
    wheels.json
    appearance.json
    browser-connector.json
    plugins.json
    actions\                     托管动作包
    backups\                     该配置档的自动备份
    sync\                        同步元数据（仅账号类型）
    profile.json                 配置档自述：ID、类型、显示名、来源、种子版本
  device\                        本机数据：程序路径映射、设备映射、窗口状态
  plugins\                       插件运行时缓存，各配置档共享
  imports\                       发现的外部副本导入前的只读快照
```

- 现有代码的所有数据文件都由 `bindings.json` 所在目录推导，因此“一个配置档 = 一个目录”可以直接映射：选中配置档等价于把该目录作为配置路径。首阶段不改文件格式。
- 配置档 ID 是创建时生成的随机稳定 ID，不使用显示名、账号邮箱或测试场景名作目录名；改名不移动目录。测试配置档另有便于命令行引用的**别名**，见下文。
- 链接目录动作包的路径属于本机数据，存于 `device\`，不进入配置档。

## 测试配置档

测试配置档是持久的：同一个别名每次启动都读写同一份数据，测试中做的修改、录制的绑定和轮盘都保留到下次，直到显式重置。

### 创建与引用

| 命令 | 作用 |
| --- | --- |
| `--profile <别名或 ID>` | 使用指定配置档启动。别名不存在时报错退出，不隐式创建。 |
| `--profile-create <别名> [--type test] [--seed <来源>] [--name <显示名>]` | 创建测试配置档后退出。来源为 `empty`（默认，即程序默认数据）、`fixture:<目录>`，或 `copy:<别名或 ID>`，`copy:default` 复制日常配置。`backup:<来源>:<热键版本>:<轮盘版本>` 使用编辑备份。合并仓库示例的 `examples` 来源尚未实现。 |
| `--profile-reset <别名>` | 用创建时记录的来源重建测试配置档。请先关闭使用该档的窗口（包括设置和独立历史窗口）。仍有窗口打开时返回 `profile_in_use`，关闭后可重试。新数据准备成功后才把原目录移入 `backups\profile-reset\`。模板缺失或读取失败时，现有配置仍可使用。 |
| `--profile-list` | 以 JSON 输出所有配置档的 ID、别名、类型、目录与默认标记。 |

Windows 上，从只读文件创建或重置测试档后，可以直接编辑副本中的热键、轮盘和动作脚本。来源文件保留只读属性。重置前的修改可在命令返回的 `backup` 目录中找到。

用 `--profile <别名> --list-package-actions` 查看测试档的动作，用 `--profile <别名> --check-action <请求文件>` 校验调用。这两项查询只读取已有配置档。`--test-workspace` 搭配查询时也需要先创建 `testing`。如果重置中断、原目录待恢复，查询会报告原因并保留备份和暂存目录。打开该配置档即可触发恢复。

从打包的 Windows 工具查询日常档或其测试档时，OmniTrigger 检测本机数据重定向，并在需要时通过系统外壳读取安装版的动作目录。相对路径的调用文件仍按发起查询时的目录解析，结果和退出码返回原终端。`--data-root` 或 `--config` 显式指向日常目录之外的夹具或缓存副本时，查询读取所选位置。

运行时校验保留发起终端的 Node 选择（`OMNITRIGGER_NODE` 或 `PATH`）和显式指定的 `OMNITRIGGER_SCRIPT_HOST`。未指定脚本宿主时，按所选配置档查找宿主。加载动作目录时会核对已登记宿主的文件大小和 SHA-256。若映像与安装清单不符，依赖它的热键、轮盘槽位和动作查询会报告 `runtime_integrity`，从来源档沿用该宿主的测试副本也能看到原因。恢复宿主后，重新加载动作目录即可刷新界面状态。

- 别名限定为小写字母、数字和 `-`，在数据根内唯一。开始菜单的“OmniTrigger 测试”使用 `testing`，其他别名可用 `--profile-create` 创建。
- 手工还原配置时，如果已登记测试档的目录位置被同名文件占用，打开、复制和重置都会报告该路径。将文件移到别处，再放回原配置目录。若上次重置留下了完整的备份和暂存目录，移开文件后直接打开测试档即可恢复。
- 手工还原后，如果目录内的 `profile.json` 属于另一份档案，打开、复制和重置都会指出身份冲突。按身份文件中的 ID 把备份放回对应目录后即可重试。已有总登记、缺少身份文件的旧备份仍可打开。
- 如果重置在旧档移入备份、新档就位前中断，下次打开测试档会核对同一次重置的备份和暂存档，找回原有热键、轮盘、动作和历史。此时使用 `--check-config` 会报告目录缺失，并保持文件原状。若备份不完整或有多组匹配，打开测试档会给出备份位置，供手动核对。
- 如果恢复数据时只找回了 `profiles\` 目录，保留各配置档原来的 ID 目录名和其中的 `profile.json`。`--profile-list` 可先查看找回的配置档。打开“OmniTrigger 测试”会重建缺失的总登记 `profiles.json`，已有热键和动作包继续从原目录加载。若总登记已存在，程序以它为准。
- 总登记缺失且重置在目录替换中途退出时，`--profile-list` 会核对同一次重置的备份和暂存档中的身份，列出原配置档。打开该档时才恢复原目录里的热键、轮盘和动作。遇到身份冲突时，程序保留现场并报告备份路径。
- 复制或重置测试档时会带入热键、轮盘、托管动作包 `actions\` 和 RaiShot 自定义动作清单 `plugins\raishot\manifest.json`。测试档可以独立修改这些动作。插件运行时、浏览器连接器的安装登记、锁文件、`.bak` 旧备份和 `device\` 会跳过。
- 浏览器连接器保存中断后留下的临时登记文件和替换备份也会跳过。它们的修改时间不会触发外部副本导入提示。
- 复制档中的轻量脚本优先使用本档安装的宿主，本档尚未安装时沿复制来源查找。如果以一个已登记的测试副本作为数据根，再用 `copy:default` 创建子档，子档也能使用外层副本继承的宿主。每一层都执行自己的动作代码、读写自己的数据。夹具可预置动作和数据，运行它们需另行安装宿主。宿主登记损坏时会报告错误，修复后再运行。
- 从日常档或其他配置档复制时，新测试档的文本剪贴板历史从空白开始。重置这类测试档时，原有历史随测试档保存在 `backups\profile-reset\`。升级安装保留已有配置档中的历史。需要预置历史的测试可在 `fixture:<目录>` 中放入合成的 `clipboard-history.json`。
- 来源配置档有未结束的 Legacy 插件升级时，复制和按此来源重置会报告失败。完成或恢复来源的升级后可以重试。已安装的动作包会随配置复制，插件安装过程留下的暂存目录只保留在原档。旧版测试档如果继承了来源的升级标记，可在来源恢复后运行 `--profile-reset <别名>` 重建，该测试档原有数据会随重置备份保留。
- 重置时，热键、轮盘和动作脚本取自种子。若曾在这个测试档单独安装轻量脚本宿主，重置会校验并保留当前登记的版本。旧版本和手工放入的宿主保存在重置备份里。若活动包已经损坏，重置回执的 `runtime_warning` 会说明原因，可在重置后的档中重新安装。
- 旧测试档里如果还留着种子来源的浏览器连接器登记，打开测试档会显示“未安装”。运行 `--profile <别名> --browser-connector refresh` 可清理该测试档的旧登记。日常档里的连接器继续使用原来的配置。
- 测试夹具放在仓库内（例如 `tests\fixtures\profiles\<场景>\`），作为版本控制下的种子；配置档本身在数据根中，不进入仓库。
- 用 `--seed fixture:<相对目录>` 创建测试档时，路径以发起命令时的工作目录为准。即使由 Windows 外壳转交启动，创建和以后重置也使用同一个夹具目录。

### 测试实例的运行约束

- 测试配置档默认**不安装 Hook**，只打开界面，避免与日常实例重复触发；需要验证真实输入时显式加 `--listen`，此时与日常实例的冲突规则见下节。
- 窗口标题带配置档显示名，例如 `OmniTrigger — 测试：浏览视图`，便于自动化按标题定位窗口和截图，不会误操作日常实例。
- 测试实例不修改 `profiles.json` 中的默认配置档，不影响下次正常启动。

### 自动化与 Agent 的推荐流程

1. 首次：`--profile-create ui-browse --seed fixture:tests\fixtures\profiles\ui-browse --name 浏览视图` 建立一个覆盖键盘、鼠标、滚轮和应用范围的测试配置档。
2. 每次验证：`--profile ui-browse` 启动，检查后退出；数据保留，下次继续使用。
3. 场景被测试改乱时：`--profile-reset ui-browse`。
4. 需要真实输入：`--profile ui-browse --listen`，验证完立即退出。

## 单实例与切换

开始菜单、普通启动和 `--settings` 共用同一配置目录和监听模式的主窗口。运行 `--settings` 会唤回窗口并打开设置页；正在录制组合时会保留录制页面。普通启动从托盘恢复当前页面。此时即使磁盘上有中断的导入，现有窗口也会继续使用当前热键。退出日常实例后再次启动，程序才会在载入热键前恢复导入。直接指定标准的 `--config bindings.json` 和更新器重启时也沿用这个窗口。

同一 Windows 会话内，支持此机制的版本只有一个实例能安装输入监听。日常窗口收进托盘或暂停时仍占用监听。此时通过 `--listen`、配置文件或数据目录打开另一配置，后开的窗口仍可编辑，但会提示监听已被占用。需要换档测试真实输入时，先退出原监听实例，再到目标窗口点击“重建监听”。测试档默认只打开编辑窗口，可以与日常监听同时使用。

在原窗口内切换到另一配置档仍属于后续设计，预期流程如下：

1. 取消正在进行的前缀暂存、长按、面板和轮盘；已消费的按下补齐释放，与暂停监听的收尾规则相同。
2. 停止旧配置档的同步任务，撤下触发快照。正在执行的动作继续完成，回执带配置档代次，不写入新配置档。
3. 加载新配置档，通过冲突检查后整体替换触发快照；失败时保留旧快照并显示结构化错误。
4. 记录新的默认配置档，下次启动沿用。

输入核心只接收新的快照，不感知配置档。

## 外部副本的发现与导入

日常实例已运行时，再次从开始菜单打开会唤回原窗口。首次打开默认日常窗口时，程序会检查 `%LOCALAPPDATA%\Packages\*\LocalCache\Local\OmniTrigger\` 中的副本。如果发现比当前数据更新且未被忽略的副本，会在载入热键前询问是否导入。选择导入会先把当前数据备份到 `backups\before-import-<时间>\`，再复制副本的顶层数据文件、托管动作包和 RaiShot 自定义动作清单。也可以本次跳过，或选择忽略并在副本下次更新时再提示。

选择“忽略”或成功导入后，程序在本机保存这次副本的内容摘要。即使副本和日常档不同，单纯刷新文件时间也能直接打开主窗口。较新副本的热键、轮盘、动作文件或其他可导入内容有变化时，仍会提示。只有时间记录的旧版本沿用原判断，直到你再次处理这份副本。

比较修改时间时也会检查 `actions\` 中的文件。程序只对时间较新且未处理的候选核对内容。若副本提供的顶层数据、动作包和 RaiShot 自定义清单都已在日常档，单纯复制文件导致的时间变化不会弹出导入提示。日常档独有的文件保留；同一个动作包按清单 ID 对应到已安装目录。若另一个较新副本确有差异，仍会提示导入那一份。来源中有尚未恢复的配置导入时，启动会跳过这份副本，继续检查其他来源。该来源恢复后会再次参与比较。

浏览器连接器沿用日常安装的登记。外部副本中的连接器路径和进程信息只对来源安装有效。已安装的连接器保留在日常配置及其导入前备份中。

日常档有未结束的 Legacy 插件升级时，启动会暂缓导入提示。如果升级发生在外部副本中，程序只跳过该来源，其他可用副本仍可导入。完成或恢复升级后，下次启动会重新检查。单独更新插件的安装暂存文件不会触发副本提示。

选择导入后，程序先备份当前配置，再读入副本。热键和轮盘通过动作包清单的 `id` 查找扩展。同一个扩展即使在副本中改过目录名，也会导入日常档原来的包目录，替换同名文件并保留本机独有的文件。新扩展与已有扩展重名时，会使用空闲目录。如果同一份配置内有多个目录声明本次要导入的同一标识，程序会提示涉及的目录，保留日常配置供你确认。

导入完成前，程序会检查合并后的动作目录。如果日常档或待导入副本中原本可加载的扩展因入口文件缺失、目录超限等原因消失，本次导入会撤回，并列出受影响的包标识。补齐文件或整理目录后可重新导入。副本中的清单可以继续引用日常档已有的入口文件。

文件被占用时会撤回本次已写入的内容。解除占用后，重新打开日常版即可重试。若进程在替换过程中退出，下次打开日常窗口会先恢复原配置。若其他程序在此期间修改了待恢复文件，程序会保留该文件和备份，并提示处理恢复冲突。

如果副本包含文本剪贴板历史，而日常档正在读写历史，本次导入会提示稍后重试。待当前操作结束后重试，刚保存的记录会进入导入前的备份。只导入热键、轮盘或动作包时，可以继续使用文本历史。

如果副本包含热键或轮盘，而日常窗口正在保存其中一项，主窗口会打开并显示本次未导入的原因。保存完成后重新启动日常版即可重试，刚保存的配置会进入导入前的备份。恢复中断的导入时同样会检查这两个文件。只导入动作包时，日常窗口仍可保存热键和轮盘。

成功导入或选择忽略后，程序在 `device\external-copies.json` 中为每个来源保留已处理的最新修改时间。恢复较早的日常备份或外部副本、从旧窗口重试保存，都不会重复提示已处理的版本。来源的修改时间同时晚于这条记录和当前日常数据时，才会重新提示。取消或导入失败后仍可重试。

如果处理记录被占用，日常窗口仍会打开。解除占用后可点「重试保存」，只补写记录，导入后编辑的热键和轮盘会保留。如果程序无法读取已有的处理记录，会保留原文件并跳过本次提示。

规划中的导入管理包括下列能力。

- 每份副本列出来源包名、最后修改时间、绑定与轮盘条数，以及与当前数据的差异摘要。
- 用户逐份选择：导入为新配置档、替换当前配置档的数据（先备份），或忽略。不自动合并，不删除原副本。
- 在 `imports\` 中长期保留可供单独查看的外部副本快照。

旧版 `--config <路径>` 保留为开发入口，表示临时配置档：直接读写该文件所在目录，不进入 `profiles.json`，不同步，界面显示“临时数据”标记，默认不安装 Hook。

## 备份与恢复

在安装版中保存对已有热键或轮盘的修改时，程序会先把即将覆盖的原文件保存在当前本机配置档中。打开“设置 → 查看配置备份”，选择 `bindings.json` 或 `wheels.json` 文件夹。编号越大的 JSON 文件保存得越晚，资源管理器的修改日期可用来查找版本。每个文件分别保留最近 20 份，以及最近 30 个 UTC 自然日中每天最后一份。相同的原文在保存重试时只留一份。

在当前档的“设置 → 从备份新建测试副本”里，分别选择热键和轮盘的版本。只恢复其中一项时，另一项保留“当前配置”。点击“校验并新建测试副本”，通过格式、场景和轮盘引用检查后才创建副本。窗口中会显示新档别名，点击“打开这个测试副本”即可核对布局。测试副本使用所选版本的原文件和来源档当前的动作包，拥有独立的编辑历史与剪贴板历史。

重启或重装后，在来源档的“设置 → 查看已有恢复副本”中选择“打开”即可继续使用原测试副本。列表按创建时间从新到旧排列，显示名称、别名和创建时选用的热键、轮盘版本。查看列表不会打开窗口。即使来源备份已清理，也能打开副本并保留其中后续的编辑。日常档和各测试档分别显示从本档直接恢复的副本。

命令行也可以从备份建档。例如，`omnitrigger.exe --profile-create restore-notes --seed backup:default:3:7` 取日常热键的第 3 份备份和轮盘的第 7 份备份。`backup:notes:current:7` 则取测试档 `notes` 当前的热键和它自己的第 7 份轮盘备份。

重置从备份创建的测试档时，程序重新读取同一来源和编号，并核对创建时记录的 SHA-256。即使来源历史被清空后又从 1 开始编号，只要备份内容变了，重置就会提示并保留测试档里的编辑。找不到备份时也会保留编辑。选为 `current` 的一项始终取来源档当前保存的内容。旧版创建的副本没有原始校验记录，第一次成功重置时会记下本次使用的备份，供以后核对。

核对布局后，要将这组文件用于日常档，可右键托盘图标选择“退出 OmniTrigger”，另存日常档当前的文件，再将核对过的 `bindings.json` 或 `wheels.json` 复制到日常档并重新打开。外部编辑器直接写入文件时由该编辑器管理历史。

在轮盘编辑器里可以将已有热键的动作复制到一个格子。需要迁移多个应用布局时，可对配置副本运行下面的命令。示例将热键 12 的完整动作复制到轮盘 `personal` 通用布局的第 4 个槽位，并更新同一轮盘中方位、场景和原动作都相同的应用槽位。每个槽位保留自己的名称。工具也能读取版本 1–4 的热键配置，包括通知和运行程序的动作，程序参数与工作目录会一并复制。

```powershell
python scripts/migrate_wheel_action.py --bindings .\copy\bindings.json --wheels .\copy\wheels.json --binding-id 12 --wheel-id personal --base-slot 4 --output .\candidate\wheels.json
```

槽位序号按 `slots` 数组从 1 开始。输出目录需已存在，候选文件由命令新建。如果动作需要较新的轮盘格式，工具只将候选文件升到所需版本。例如，把剪贴板扩展动作复制到版本 1 的轮盘会生成版本 3 的候选。把对应的 `bindings.json` 放到候选目录后，用 `omnitrigger.exe --config .\candidate\bindings.json --check-config` 校验，再在测试档中核对布局。

配置档重置和日常数据导入还会保存整份旧配置。设置内直接覆盖当前档和同步合并快照属于后续设计。

## 迁移

首次升级到配置档版本时：

1. 解析真实数据根；处于重定向上下文时先按上文脱离。
2. 把根目录下现有的 `bindings.json`、`wheels.json`、`appearance.json`、`browser-connector.json`、`plugins.json` 和 `actions\` 复制进一个名为“我的配置”的本地配置档，设为默认；原文件保留在原位置，并写入迁移标记，迁移可重复执行且不重复导入。
3. 扫描并提示外部副本，处理方式见上节。

## 与账号的关系

| 操作 | 行为 |
| --- | --- |
| 本地配置档关联账号 | 云端为空时上传；云端已有数据时由用户选择：使用云端、上传本地或另存为新配置档。不自动合并、不覆盖。 |
| 新设备登录 | 新建账号配置档并下载数据；本机已有的本地配置档保持不变。 |
| 退出登录 | 停止同步、清除会话凭据，配置档转为本地类型继续可用，并标记“已退出，未同步”。 |
| 删除 | 删除本机配置档、删除云端数据和退出登录是三个独立操作，均需确认。 |

- 每个配置档最多关联一个账号；同一账号在本机只对应一个配置档。
- 测试配置档不能关联账号；需要同步时先复制为本地配置档。
- 本机数据（`device\`、`plugins\`）与运行期数据不随配置档或账号同步。

## 界面

- 侧栏监听状态卡下方显示当前配置档名称；测试和临时配置档使用醒目色块，一眼可见当前不是自己的数据。
- 点击配置档名称弹出切换列表：选中即切换，列表底部是“管理配置档”。
- “设置 → 配置档”是管理入口：新建（空白 / 从示例 / 复制当前）、改名、重置测试数据、导入外部副本、导入导出、备份恢复和关联账号；同时显示数据根位置及其解析来源。

## 实现顺序

1. 数据根解析与重定向检测：探针、脱离打包上下文重启、无法脱离时阻断提示，`--data-root` 与 `OMNITRIGGER_HOME`。
2. 配置档目录与 `profiles.json`，旧数据迁移为“我的配置”；`--profile`、`--profile-list`，窗口标题显示配置档。
3. 测试配置档：`--profile-create`、`--profile-reset`、`examples` 与夹具种子，默认不安装 Hook，`--listen`。
4. 单实例：监听实例互斥与参数转交，测试实例按配置档互斥。
5. 外部副本发现与导入，保存前自动备份与恢复。
6. 运行中切换配置档，侧栏标识与设置页管理界面。
7. 账号关联与同步，按[账号工作区与同步设计](ACCOUNT_WORKSPACE.md)的实现顺序推进。

每一步都以独立数据根运行集成测试：同一测试别名两次启动读到相同数据、重置后恢复种子、重定向探针在模拟路径下判定正确、两个监听实例只有一个安装 Hook。
